## 4. Primary-source requirements (SLO, burn-rate, alert thresholds)

### 4.1 What an SLO must declare (R11, R12)

- **SLI as a ratio** — "we generally recommend treating the SLI as the ratio of two numbers: the number of good events divided by the total number of events", e.g. successful/total requests, and using one consistent style "allows you to take better advantage of tooling: you can write alerting logic, SLO analysis tools, error budget calculation, and reports to expect the same inputs: numerator, denominator, and threshold" (R11, "What to Measure: Using SLIs"). A spec→implementation split is required: the SLI specification (what matters to users) vs. the SLI implementation (how it is measured — logs, load balancer, probers, client instrumentation), each with quality/coverage/cost trade-offs (R11).
- **Error budget = 100% − SLO** — "the error budget is 100% minus the SLO. For example, if you have a 99.9% success ratio SLO, then a service that receives 3 million requests over a four-week period had a budget of 3,000 (0.1%) errors over that period" (R11). R12's worked document repeats the arithmetic: "Each objective has a separate error budget, defined as 100% minus the goal" (R12).
- **100% is the wrong target** — even with redundancy there is a nonzero simultaneous-failure probability, customers don't experience 100% across the chain, each extra nine costs more for diminishing utility, and a 100% SLO forbids all change (R11, "Reliability Targets and Error Budgets").
- **Time window** — rolling windows track user experience better than calendar windows; a four-week rolling window is "a good general-purpose interval", complemented by weekly summaries and quarterly reports (R11, "Choosing an Appropriate Time Window"). R12's example "uses a four-week rolling window" (R12).
- **Stakeholder agreement + error-budget policy** — the SLO needs product, development, and SRE agreement, plus a written error-budget policy stating what happens when the budget is exhausted and who acts (R11). A bare threshold with no policy is "an SLO without teeth" (R11).
- **Document fields** — authors, reviewers, approvers, approval date, revisit date, service description, SLI implementations, error-budget calculation, rationale (including whether numbers are experimental, observational, or ad hoc), plus caveats about what the measurement misses (R11; R12).

Mapping to CGO: the only threshold triple in the repo is 220 ms / 95% / (no window) (`pkg/metrics/cost.go:80-83,105`); no SLI numerator/denominator pair, no window, no error-budget arithmetic, no authors/dates/rationale document exists in the three files. The SLO window length for CGO is therefore `unverified — primary source not found` (no repo primary states it; R11's four weeks is a recommendation, not a CGO decision).

### 4.2 Burn rate (R10)

- **Definition** — "Burn rate is how fast, relative to the SLO, the service consumes the error budget"; burn rate 1 = consuming at a rate that exhausts the budget exactly at the end of the window; for a 99.9%/30-day SLO a constant 0.1% error rate is burn rate 1 (R10, approach 4). Table 5-4 (R10): burn 1 → 0.1% → 30 days; burn 2 → 0.2% → 15 days; burn 10 → 1% → 3 days; burn 1000 → 100% → 43 minutes.
- **Recommended multi-burn-rate parameters** (R10, Table 5-8, approach 6): page at long 1h / short 5m / burn 14.4 (2% of budget); page at long 6h / short 30m / burn 6 (5%); ticket at long 3d / short 6h / burn 1 (10%). Short window guideline: "make the short window 1/12 the duration of the long window" (R10, approach 6). Multiple burn rates let priority follow response-time need: "If an issue will exhaust the error budget within hours or a few days, sending an active notification is appropriate. Otherwise, a ticket-based notification to address the alert the next working day is more appropriate" (R10, approach 5).
- **Alert quality trade-offs** — every alerting strategy is judged on precision, recall, detection time and reset time (R10, "Alerting Considerations"). Approach 1 (alert when a short-window error rate ≥ SLO threshold) has good detection but low precision — total budget spend per alert can be ~0.02% of monthly budget (R10, approach 1, Table 5-1). Approach 3 (`for:` duration as the window) is explicitly **not recommended** for SLO alerting: "Poor recall and poor detection time: because the duration does not scale with the severity of the incident, a 100% outage alerts after one hour, the same detection time as a 0.2% outage" (R10, approach 3, Table 5-3).

### 4.3 Prometheus rule requirements (R2, R3, R4, R6, R7)

- **File structure** — rule files are YAML with `groups: [{name: <string>, rules: [...]}]`; group `name` must be unique within a file; `interval`/`limit`/`query_offset` optional with defaults; `record:` names must be valid metric names, `alert:` names valid label values (R2).
- **Alert semantics** — an alerting rule is `alert:` + `expr:` with optional `for: <duration>` (pending until the expression stays true for that duration), optional `keep_firing_for: <duration>` (keeps firing after the condition clears; default 0s = deactivate on first non-matching evaluation), and templated `labels:`/`annotations:` (R3). Without `for:` an alert "will become active on the first evaluation" (R3). `$labels`, `$externalLabels`, `$value` are available in templates (R3).
- **Recording-rule correctness** — names follow `level:metric:operations` (newest first), metric name unchanged except stripping `_total` after `rate()`/`irate()`; aggregate numerator and denominator separately then divide; always specify `without (…)`; "Do not take the average of a ratio or average of an average, as that is not statistically valid" (R4).
- **Function typing** — "`rate` should only be used with counters (for both floats and histograms)" and is best suited for alerting/slow-moving counters (R6, "`rate()`"). "`absent(v)` returns a 1-element vector with the value 1 if the vector passed to it has no elements… useful for alerting on when no time series exist" (R6, "`absent()`"); `absent_over_time()` does the same over a range (R6).
- **Testing** — `promtool test rules <test.yml>` evaluates `input_series` fixtures against `alert_rule_test` (expected firing alerts per `alertname` at `eval_time`) and `promql_expr_test` (expected samples) (R7).

### 4.4 Alerting & Alertmanager requirements (R1, R5, R8, R9)

- **Split of duties** — Prometheus figures out what is broken right now; Alertmanager adds "summarization, notification rate limiting, silencing and alert dependencies" (R3, "Sending alert notifications"); Prometheus must be configured to discover/talk to Alertmanager instances (R1).
- **What to alert on** — "keep alerting simple, alert on symptoms, have good consoles to allow pinpointing causes, and avoid having pages where there is nothing to do"; alert on high latency/error as high in the stack as possible so user-visible symptoms page once; metamonitoring alerts must prove the monitoring itself works (R5).
- **Naming** — no strict restriction, but "the community has rallied around using CamelCase for their alert names" (R5).
- **Alertmanager concepts** — grouping by labels into one notification, inhibition (mute target alerts while a source alert fires), silences (matchers + time), and HA (don't load-balance Prometheus→Alertmanager traffic; point Prometheus at all instances) (R8).
- **Alertmanager config** — `route:` tree with `receiver`, `group_by` (e.g. `[cluster, alertname]`), `group_wait`/`group_interval`/`repeat_interval`; `receivers:` list; `inhibit_rules:` with source/target matchers and `equal:` labels; `time_intervals:` for mute/active windows; validate with `amtool check-config` (R9).

### 4.5 Go module requirements (R13)

- A module is identified by the module path in `go.mod`'s `module` directive; it is "a collection of packages that are released, versioned, and distributed together" (R13). `cgo-slo` as an independent repo therefore needs its own `go.mod` + module path; pre-1.0 versions carry no compatibility promise, 1.0 is that promise (general versioning discipline recorded in the prior pass, `docs/research/2026-11-07-module-prometheus-metrics.md:153` — versioning semantics themselves: R13 "Versions").
- The `go` directive declares the minimum Go version; since Go 1.21 it is mandatory and newer toolchains refuse older modules (R13, "`go` directive").
- Major version ≥2 requires a `/vN` suffix because "packages in a new major version of a module are not backwards compatible" and need distinct import paths (R13, "Major version suffixes"). A generator that changes its public rule/runbook schema incompatibly must bump the suffix, not silently change output.

## 5. Gap analysis (current → SLO-grade, ordered by severity)

1. **There is no SLO in the rules — only a precomputed breach flag.** `CGO_deadline_breach_sustained` fires on `cgo_cap_sla_breach == 1` (`deploy/prometheus/rules.yml:7`) — i.e. on a boolean computed elsewhere from 220 ms/95% (`pkg/metrics/cost.go:99-112`) — with no SLI ratio, no numerator/denominator, no target, no window, no error budget anywhere in the file. That is R10 approach 1 ("alert if the error rate over [a short window] exceeds the SLO"), which R10 shows has low precision: a 0.1% error rate for 10 minutes alerts while consuming only 0.02% of the monthly budget (R10, Table 5-1). R11 requires the SLI ratio, the error budget (100% − SLO), and the window to be stated so tooling can share "the same inputs: numerator, denominator, and threshold" (R11) — none are stated here. The 220/95 values themselves are at least honestly labelled as an operator objective, not an external mandate (`pkg/metrics/cost.go:75-79`).
2. **The recording rule is wrong twice.** `avg(rate(cgo_cap_deadline_ok_pct[5m]))` (`deploy/prometheus/rules.yml:5`) applies `rate()` — which "should only be used with counters" (R6) — to a 0–100 percentage gauge (R11: ratio-style SLI in 0–1 terms), then takes `avg()` of the ratio, which R4 forbids ("Do not take the average of a ratio or average of an average"). The correct shape per R4 is numerator and denominator recorded separately and divided, with a `without` clause; per R6 a percentage window belongs in `avg_over_time()`. Even if the input metric existed, this expression cannot produce a valid SLO ratio.
3. **`for:` is used as the entire SLO mechanism.** All three alerts rely solely on `for: 5m/10m` (`deploy/prometheus/rules.yml:8,15,22`). R10 approach 3 warns against exactly this for SLO alerting: duration "does not scale with the severity of the incident" — a 100% outage and a 0.2% outage alert after the same hour, and a fluctuating SLI may never alert (R10, Table 5-3). No burn-rate alert exists at all (R10 approaches 4–6): there is no long/short window pair, no 14.4/6/1 burn threshold, no page-vs-ticket split by budget-consumption rate (R10, Table 5-8).
4. **`CGO_probe_dead` cannot detect the absence it is named for.** `rate(cgo_audit_load_measured_total[5m]) == 0` (`deploy/prometheus/rules.yml:14`) only matches when the series exists and its rate is zero; a missing series yields an empty vector, and `== 0` on an empty vector matches nothing. R6's prescribed shape for "no time series exist" is `absent()` / `absent_over_time()` (R6). Additionally, if the counter never increments while idle, `rate == 0` is the *normal* state, so the alert is inverted — it needs a real heartbeat counter that actually increments, or the `absent_over_time` form.
5. **No multiwindow, no reset discipline, no `keep_firing_for`.** R10 approach 6 (most recommended) pairs a long window with a short window at 1/12 the long duration so alerts stop firing soon after the burn stops, instead of lingering for the full long window (R10, Fig. 5-6). No rule sets `keep_firing_for:`; R3 defaults it to 0s, so alerts deactivate on the first non-matching evaluation — flap-prone by construction (R3). Whether flapping is acceptable for CGO capacity is `unverified — primary source not found` (no repo primary states a flap policy; R3 only defines the mechanism).
6. **No Alertmanager layer at all.** No `alertmanager.yml`, no `route:` tree, no `receivers:`, no `inhibit_rules:`, no `time_intervals:` (R9), and no Prometheus service to consume `rule_files` (R2) — `deploy/docker-compose.yml:1-13` is one service only. Groups/inhibition/silences (R8) therefore cannot happen: `severity: critical` vs `warning` (`deploy/prometheus/rules.yml:10,17,24`) is decoration. Suppression of duplicate page+ticket notifications — which R10 approach 5 explicitly requires ("you need to implement alert suppression" when multiple burn windows match) — has no home.
7. **Runbook is disconnected from the alerts and missing SLO-document fields.** `smoke-alerts.md` never names `CGO_deadline_breach_sustained`/`CGO_probe_dead`/`CGO_iface_invalid`, never states a threshold, window, burn rate, or budget, and never gives escalation by severity (R10: page vs ticket by exhaustion horizon). Its six procedures cover auth/nginx/rollback/target-down/bench/corpus — useful ops, but none maps to a firing alert's first three actions. Under R11/R12 an SLO artifact must carry authors/reviewers/approvers/dates, SLI spec + implementation, error-budget arithmetic and rationale; this file carries none. Each alert's annotations hold only `summary:` (R3 permits `description:` and runbook links — both absent).
8. **The verifier is blind to this entire surface.** Zero references to `rules.yml`/`promtool`/`slo`/`smoke-alerts` in `tools/` (grep, §1); `LINK_FILES` excludes both files (`tools/verify.py:392-393`); no gate runs `promtool check rules` (R2) or `promtool test rules` (R7); no fault proof can catch a broken recording rule. `tools/verify.py`'s six gates prove corpus, provenance, Go tests, CLI exit contract, hygiene and links (`tools/verify.py:455-462`) — all real, none relevant to whether an SLO alert fires. The selftest mechanism (`prove_*`, `tools/verify.py:510-516`) is the right pattern and is simply missing for rules.
9. **Alert naming deviates from the community convention, and one name carries a colon correctly but teaches nothing.** `CGO_deadline_breach_sustained` etc. are SCREAMING_SNAKE; R5 records the community rallying on CamelCase (SHOULD-level, not a parse break). The recording rule `cgo:slo:deadline_ok_pct_5m` correctly uses colons (R2 reserves them for recording rules) and roughly matches `level:metric:operations` (R4) — but `pct` embeds a non-ratio unit, where R4/R11 expect a ratio. Renaming is a breaking change for every PromQL/dashboard, so it must happen before first tag (§6, slice 1).
10. **No SLO document, no error-budget policy, no window decision.** R11 requires stakeholder agreement + a written error-budget policy before an SLO has "teeth"; R12 shows the document shape. The repo has Go constants + a 21-line runbook. Which stakeholders approved 220 ms/95%, over what window, and what happens on budget exhaustion is `unverified — primary source not found` in the three files (the constants' comment only says what the numbers are *not* — `pkg/metrics/cost.go:75-79`).
11. **Low-traffic caveat unaddressed.** R10 warns that for low-rate services a single failure can read as a 1000x burn rate and page spuriously, and lists mitigations (synthetic traffic, combining services, retry/fallback, lowering the SLO or widening the window) (R10, "Low-Traffic Services"). A link-audit probe is plausibly low-rate, but the three files make no such analysis — whether CGO's audit rate triggers the caveat is `unverified — primary source not found` (no traffic numbers in scope).

## 6. Target tool: `cgo-slo` as independent repo + runbook generator

A separate, tiny repo — not a package inside `cgo` — that owns the SLO declaration, the generated rules/runbook, and the verification of both. It never runs the bench, never touches the frozen corpus, and never scrapes for measurements itself (the exporter does that); it only *declares* how measurements become SLOs and alerts.

### 6.1 Shape (per R13, R2/R3/R4, R8/R9, R11/R12)

- **Module**: own `go.mod` with its own module path and `go` directive (R13) — e.g. `module <host>/cgo-slo` with `go 1.25` mirroring `go.mod:3`. Zero third-party deps to start (stdlib only, mirroring `tools/verify.py:4-6`); the generator is a pure function `Spec → {rules.yml, rules_test.yml, alertmanager.yml snippet, runbook.md}`. Pre-1.0 may change the spec schema freely; 1.0 is the compatibility promise (R13 versioning). An incompatible schema change later needs a `/vN` suffix (R13, "Major version suffixes").
- **Declaration** (`slo.yaml`, single source of truth): for each SLO — name, SLI spec ("what matters"), SLI implementation (metric names for numerator + denominator, R11), target (e.g. 0.95), window (default 28d/4w per R11 recommendation, explicitly recorded), burn-rate table (default R10 Table 5-8: 14.4/1h+5m page, 6/6h+30m page, 1/3d+6h ticket), severities, owners, authors/reviewers/approvers/dates (R11/R12 fields), and per-alert runbook steps. One SLO spec produces all artifacts — no hand-edited `rules.yml` drift.
- **Generator** (`cmd/cgo-slo/main.go`, flags `--spec slo.yaml --out dir/`, `--check` for CI): emits
  1. `rules.yml` — recording rules as numerator/denominator rates + ratio with `without` clauses (R4), named `level:metric:ratio_rate<window>`; alerting rules as multiwindow multi-burn-rate pairs (R10 approach 6) with `for:` small or absent (R10 warns against duration-as-window), `keep_firing_for:` explicit (R3), CamelCase alert names (R5), `severity: page|ticket` (R10), and `summary:` + `description:` + `runbook_url:` annotations using `$labels`/`$value` templating (R3).
  2. `rules_test.yml` — `promtool test rules` harness (R7) with `input_series` fixtures per alert: firing at burn thresholds, non-firing on healthy data, `absent_over_time` firing on a missing series (R6), recording-rule ratio correctness (R4).
  3. `alertmanager.yml` snippet — `route:` tree splitting `severity="page"` vs `severity="ticket"`, `group_by: [alertname]`, `group_wait`/`group_interval`/`repeat_interval` per R9 defaults or tuned, `inhibit_rules:` suppressing the ticket variant while the page variant fires (R10 approach 5 suppression requirement; R8 inhibition), receivers left as named placeholders.
  4. `runbook.md` — auto-generated per-alert pages (one file or one section per alertname) carrying the R11/R12 fields (SLO target, window, error budget arithmetic, burn-rate explanation, first three actions, verification, escalation, authors/dates) plus the hand-written ops sections migrated from `smoke-alerts.md` (auth rotation `docs/runbooks/smoke-alerts.md:3-6`, rollback `docs/runbooks/smoke-alerts.md:11-12`, target-down `docs/runbooks/smoke-alerts.md:14-15`, bench fail-closed `docs/runbooks/smoke-alerts.md:17-18`, corpus seal `docs/runbooks/smoke-alerts.md:20-21`) — generated structure, hand-written steps marked as such.
- **Verifier** (`cgo-slo verify`): ports the six `tools/verify.py` gates that transfer (frozen-seal, provenance enums, hygiene, links — now *including* `rules.yml` and `runbook.md` in the scanned set, fixing §5.8) and adds two new gates in the same `prove_*` fault-proof style (`tools/verify.py:510-516`): `promtool check rules` exit-0 gate (R2) and `promtool test rules` green gate (R7), each with a fault proof (a deliberately broken rule must be caught). Exit contract 0/1/2 preserved (`tools/verify.py:35-36`).
- **Composition**: in this repo, `cgo-slo generate` output replaces `deploy/prometheus/rules.yml` verbatim; `deploy/docker-compose.yml` gains a Prometheus service mounting the generated file as `rule_files` (R2) and an Alertmanager service configured to talk to it (R1); the exporter (separate prior-pass tool, `docs/research/2026-11-07-module-prometheus-metrics.md:147-169`) emits the numerator/denominator counters the generated recording rules consume. No SLO logic lives in the exporter; no measurement logic lives in `cgo-slo`.

## 8. Anti-toy criteria (what would make `cgo-slo` unacceptable as a standalone tool)

1. **No SLO-free thresholds.** Every alert expression traces to a spec line stating SLI numerator, denominator, target, window and burn rate (R11; R10 Table 5-8). A rule whose only justification is "it was in `rules.yml`" fails review.
2. **No `rate()` on gauges, no averaged ratios.** Generated recording rules pass R4/R6: counters only through `rate()`, ratios built from separately aggregated numerator/denominator with `without` clauses. `avg(rate(..._pct...))` surviving in any generated file is the toy signal.
3. **No duration-as-SLO-window.** `for:` never substitutes for a burn-rate window pair (R10 approach 3 / Table 5-3). An alert that would take the same hour to fire at 100% outage and at 0.2% error is rejected.
4. **Absence is detectable.** A missing series fires via `absent_over_time()` (R6) in a `promtool test rules` fixture (R7), not via `== 0` on an empty vector. `rate(...)==0` surviving is a toy.
5. **`promtool` is a gate, not an aspiration.** CI runs `promtool check rules` (R2) and `promtool test rules` (R7) with firing and non-firing fixtures, plus a fault proof that a broken rule is caught (mirroring `tools/verify.py:510-516`). A rules file never parsed by `promtool` is §5.8 forever.
6. **Alertmanager exists and is validated.** `amtool check-config` SUCCESS (R9); page-vs-ticket routing and page-over-ticket inhibition are in the shipped config (R8; R10 approach 5). Severities that route nowhere are decoration, not alerting (R1).
7. **Runbook is generated and linked.** Every alertname has a runbook section carrying target, window, budget arithmetic, actions and escalation (R11/R12), and every alert carries a `runbook_url:` annotation (R3). An unlinked 21-line ops list (`docs/runbooks/smoke-alerts.md`) is not a runbook.
8. **Independent module identity.** `cgo-slo` has its own `go.mod` module path and `go` directive (R13); an incompatible spec-schema change bumps the major version suffix (R13) instead of silently changing generated rules. A "standalone" tool that is really a Python script inside `cgo` (`tools/verify.py:1`) plus a YAML file nobody loads is not standalone.
9. **Independent proof of firing.** At least one out-of-tree Prometheus evaluation of the generated rules fires on synthetic burn-rate series and stays silent on healthy series (R7). If the only proof is string-matching the generated YAML, the tool is a template, not an SLO tool.
