## 1. Responsibility

`deploy/nginx/cgo.conf` (35 lines, `deploy/nginx/cgo.conf:1-35`) is the sole S1 boundary artifact: a TLS-terminating reverse proxy in front of `cgo --serve` on `127.0.0.1:9090` that enforces per-IP leaky-bucket rate limits, split into a reads zone and a mutations zone, and rejects over-burst requests with a fixed status code. ### 4.2 HTTP semantics: 503 vs 429, Retry-After (R2, R3)

- **503 is overload, not per-client limiting.** RFC 9110 §15.6.4: "The server is currently unable to handle the request due to a temporary overload or scheduled maintenance, which will likely be alleviated after some delay. The server MAY send a Retry-After header field to suggest an appropriate amount of time for the client to wait before retrying the request." (R2 §15.6.4). The conf's `limit_req_status 503;` (`deploy/nginx/cgo.conf:9`) and `docs/deploy.md:180`'s "receive `503`" therefore tell clients the *service* is overloaded when the truth is the *caller* exceeded a per-IP bucket.
- **429 is the per-caller rate-limit code, and it is not in RFC 9110.** RFC 6585 §4: "The 429 status code indicates that the user has sent too many requests in a given amount of time ('rate limiting'). The response representations SHOULD include details explaining the condition, and MAY include a Retry-After header… Responses with the 429 status code MUST NOT be stored by a cache." (R3 §4). RFC 9110 §15.5 lists 4xx codes up to 426 only (R2 §15.5) — 429 lives in R3, not R2. A `cgo-ingress` release must record the 503-vs-429 decision explicitly: keeping 503 is nginx-default-compatible (R1 `limit_req_status` default is 503) but semantically overload; switching to 429 is semantically precise but changes client retry/monitor behaviour.
- **Retry-After is optional in both specs.** RFC 9110 §10.2.3 defines the `Retry-After` field; RFC 9110 §15.6.4 and RFC 6585 §4 both say the server MAY/SHOULD include it (R2 §15.6.4, §10.2.3; R3 §4). The conf emits no `Retry-After` anywhere in `deploy/nginx/cgo.conf:1-35`. Whether nginx's `limit_req` can inject it natively (vs `error_page` + `add_header` workaround) is **`unverified — primary source not found`** in R1 this pass — R1 never mentions `Retry-After`.
- **Cache behaviour differs.** RFC 6585 §4 mandates "MUST NOT be stored by a cache" for 429 (R3 §4); RFC 9110 §15.6.4 imposes no such blanket rule for 503 (R2 §15.6.4). A proxy chain that caches 503s will keep serving the rejection after the bucket drains — the standalone tool must state its cache stance.

### 4.3 Observability of rate limits (R4, R5, R1)

- **Prometheus text contract.** As of Prometheus 2.0 "all processes that expose metrics to Prometheus must use a text format, by default" (R4, intro); text format requires `Content-Type: text/plain` with `version=0.0.4` (R4 "Basic info"), `# HELP`/`# TYPE` lines with exactly one of each per metric and TYPE before the first sample (R4 "Comments, help text, and type information"), label-value escaping of `\`, `"`, LF as `\\`, `\"`, `\n` (R4 sample syntax), unique metric+labels per line (R4 "Grouping and sorting"), and `_sum`/`_count`/`_bucket{le}` conventions for histograms (R4 "Histograms and summaries"). Since Prometheus 3.0, "scrape targets must return a valid `Content-Type` header… If the `Content-Type` is missing… the scrape will fail" (R4 "HTTP Content-Type requirements").
- **OSS nginx cannot observe limit_req via metrics.** R5: "NGINX exposes a handful of metrics via the stub_status page. NGINX Plus provides a richer set of metrics via the API" and the exporter "fetches the metrics from a single NGINX or NGINX Plus, converts the metrics into appropriate Prometheus metrics types and finally exposes them via an HTTP server to be collected by Prometheus" (R5 Overview). The OSS metric table (R5 "Metrics for NGINX OSS") lists only `nginx_connections_*` and `nginx_http_requests_total` — no per-zone rate-limit counters. The Plus table (R5 "HTTP Requests Rate Limiting") defines `nginxplus_limit_request_passed`, `nginxplus_limit_request_rejected`, `nginxplus_limit_request_delayed`, `nginxplus_limit_request_rejected_dry_run`, `nginxplus_limit_request_delayed_dry_run`, all with label `zone` (R5).
- **Consequence for `cgo-ingress` on OSS nginx.** There is no supported per-zone `passed/rejected/delayed` counter to scrape; the only in-R1 observability hook is the `$limit_req_status` embedded variable (R1: `PASSED`, `DELAYED`, `REJECTED`, `DELAYED_DRY_RUN`, `REJECTED_DRY_RUN`) consumed via access/error logs, plus `limit_req_log_level` (R1). The conf sets neither a `log_format` with `$limit_req_status` nor a `/stub_status` location, so rejections are invisible except as 503s in default logs. Whether a log-to-Prometheus bridge (e.g. file tail + `promtail`) is the intended OSS path is **`unverified — primary source not found`** in this pass.
- **Plus exposure path, for reference.** If the tool targets NGINX Plus, status info per zone "can be obtained or reset with the API since 1.17.7" (R1 `limit_req_zone` commercial note) and the exporter surfaces it as the five counters above (R5). The OSS/Plus fork must be an explicit release choice, not an accident.

## 8. Anti-toy criteria (what would make `cgo-ingress` unacceptable as a standalone tool)

A submission fails review if any of these holds:

1. **Undeployable as shipped.** `nginx -t` fails on the committed conf (missing certs, port collision) — the current state per §5.1-5.2. A released ingress must pass `nginx -t` in CI.
2. **Conflated rejection semantics.** 503 returned for per-IP limiting with no documented rationale and no `Retry-After`, despite R2 §15.6.4 (overload) and R3 §4 (429 per-caller, MUST-NOT-cache). Silence about 503-vs-429 is a toy signal.
3. **Invisible limiting.** No per-zone `passed/rejected/delayed` signal on the declared nginx flavour — on OSS this means no `$limit_req_status` logging and no log pipeline (R1 variable unused, R5 OSS table has no limit series). Rate limiting you cannot observe is not a control.
