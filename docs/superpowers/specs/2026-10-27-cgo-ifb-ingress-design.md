# CGO Ingress IFB Shaping — Design Specification

*Date: 2026-10-27 · Status: proposed · Slice 6 of the `epbfBBR.md`
overhaul · Branch: `rebuild/plan1-economics-audit` · Target bench: Ubuntu
24.04 LTS, Linux 6.8, amd64.*

This slice adds the missing download side of the remediation and of the
campaign: Linux ingress shaping through an IFB, the corresponding RouterOS
LAN-interface queue tree, and a direction-aware report. It is engine-first.
The Linux path is not "verified" until the live acceptance task runs on the
6.8 bench; the Windows gates prove command generation and orchestration only.

---

## 0. Context

`pkg/remediate` emits only egress configurations today: `LinuxTC` attaches a
root qdisc to `Link.Interface`, and `RouterOS` parents a queue tree on
`Link.RouterOSInterface`. That is correct for upload. It cannot shape a
download, because the packets are already arriving when a client-side egress
qdisc would see them. `epbfBBR.md` Directive III.C states the problem and
prescribes the standard Linux answer: redirect the WAN ingress to an
Intermediate Functional Block (`ifb0`) and put CAKE on the IFB, where the
redirected packets are egress and can be queued.

`pkg/audit.BuildReport` today sizes the remediation from
`res.ThroughputMbps` only. For a `direction=down` audit that field is the
**down** headline (`pkg/audit/audit.go` sets it from the down window), so the
number is right but the emitted commands are still upload commands against
the wrong device. For `direction=both`, `res.ThroughputMbps` is the up
headline and `res.ThroughputDownMbps` is the down mirror; only the up side is
currently remediated. The hard-coded report evidence file
`data/audit-report-fixture.md` is not tracked and is regenerated by its test.

The campaign is egress-only too: `RunEvent` resets the shaper device and
calls `qdisc.ApplyShaper` on `e-srv` (up) or `e-wan` (down) in `ns_edge`.
There is no IFB in `kit/cgo-bench-dualns.sh`, and `Deps` has no shape mode.
The frozen corpus is untouched by all of this; IFB cells are new runs with
their own provenance.

### 0.1 In scope

- `pkg/remediate`: `LinuxTCIngress`, `RouterOSIngress`, and
  `Link.RouterOSLanInterface`.
- `pkg/qdisc`: `ApplyIngressShaper` and a read-only `CheckIngress` preflight.
- `pkg/audit`: direction-aware `BuildReport`; additive
  `linux_tc_ingress` / `routeros_ingress` report fields and Markdown
  sections.
- `pkg/campagne`: opt-in `ShapeMode=ingress`, IFB preflight before any qdisc
  mutation, IFB placement, cleanup, and stats.
- `cmd/cgo` / `pkg/api`: `--ros-lan` and `routeros_lan` plumbing.
- `kit/cgo-bench-dualns.sh` / `kit/run-dualns.sh`: opt-in `ifb0` plumbing
  and checks, never on by default.
- Tests, methodology docs, Windows gates, and a blocked live-acceptance task.

### 0.2 Out of scope

- BBRv3, eBPF, trace-driven `.dist`, IFB on the edge-router WAN ingress,
  a modeled LAN behind the client, UI changes, and the thesis chapter.
- Ingress shaping for upload or for `direction=both` campaigns. `both` would
  need two independent shape points and two cleanup owners; it is refused
  rather than approximated.
- RouterOS IFB emulation. RouterOS has no IFB; the slice emits its documented
  LAN-interface queue tree instead.
- Any change to `telemetry.csv`, `link_audit.csv`, `aqm_eval.csv`, or
  `data/runs/`.

### 0.3 Success criteria

1. `remediate.LinuxTCIngress` emits an ordered, idempotent command set:
   ingress qdisc on the WAN interface, `matchall` + `mirred` redirect to
   `ifb0`, and the requested shaper/AQM on `ifb0`; CAKE includes `ingress`.
2. `remediate.RouterOSIngress` emits an idempotent RouterOS queue tree
   parented on the named LAN interface, using `cake-flowmode=dual-dsthost`
   for CAKE, and its cleanup cannot delete the upload objects.
3. `BuildReport` on `direction=down` emits only ingress remediation; on
   `direction=both` it emits both directions with their own measured
   capacities; a missing down capacity is named, never silently zeroed.
4. A campaign cell with `ShapeMode=ingress` refuses anything but
   `bench=dualns` + `direction=down`, runs a read-only IFB preflight **before**
   the first qdisc mutation, shapes `ifb0`, and polls `ifb0` for drops/bytes.
5. The egress campaign path is byte-identical when `ShapeMode` is unset.
6. The bench `--ingress on` creates the IFB plumbing, refuses a download
   egress CAKE on `e-wan`, and `down` removes everything with the namespaces.
7. Windows tests/vet and `GOOS=linux GOARCH=amd64 go build ./...` stay green;
   the frozen guard stays at **159 runs / 208 valid lines**.
8. No claim of live IFB acceptance until Task 9 runs on Linux 6.8.

## 2. What ingress shaping is, and what it is not

`tc` qdiscs are attached to egress. An `ingress` qdisc is a hook, not a
shaper: it can filter, police, or redirect, but it cannot build the queue the
AQM needs. The standard Linux pattern is:

```
WAN ingress ──► ingress qdisc ──► matchall ──► mirred egress redirect ──► ifb0
                                                                          │
                                                          root CAKE/… ────┘
```

Once redirected, the packet is egress on `ifb0`, so an ordinary root qdisc can
queue and drop it. `ifb0` is a software device; it adds a queue and a copy of
the packet, not a new link. The AQM's drops happen on the receiving host,
**after** the packet has already crossed the real link. That is the point:
the sender is forced to back off by loss/RTT, because the receiver cannot
reach into the sender's qdisc. It is also the limit: the bytes were already
carried, so ingress drops do not save link capacity; they protect the local
queue. `epbfBBR.md` Directive III.C says this explicitly ("already traversed
the link before CAKE can choose what to do with it").

Three consequences drive the design:

1. **Do not double-shape.** If the download is already rate-limited by an
   egress CAKE on `e-wan`, the IFB queue is downstream of the bottleneck and
   never fills. The ingress bench must leave `e-wan` unshaped.
2. **Do not read `ingress` as "free".** CAKE's ingress mode counts dropped
   packets into the shaped byte count and keeps a minimum queue per flow.
   Drop counters are not interchangeable with egress drop counters.
3. **Do not claim dwell time.** The measured RTT includes the emulated link
   (netem) plus the IFB queue. There is no kernel timestamp that separates
   them; the report must not present `RTT - idle` as "queue dwell" at the
   remote link.

### 2.1 Linux prerequisites

- `ifb` device support (`modprobe ifb`, or built-in).
- `sch_ingress`, `cls_matchall`, and `act_mirred` (module or built-in).
- `tc` from iproute2 with CAKE support.
- Root or passwordless sudo for `ip`/`tc`/`modprobe` in the target namespace.

The bench's `need_modules` loads `ifb`, `sch_ingress`, `act_mirred`, and
`cls_matchall`; the production remediation script loads `ifb` and assumes the
distribution's `tc`/kernel provides the rest. If any prerequisite is missing,
the first `tc` command fails; the campaign preflight fails earlier and with a
named reason.

## 3. Bench topology

The existing four-namespace bench is unchanged:

```
ns_client          ns_wan_emulator        ns_edge_router        ns_server
c-cli ◄──────────► c-wan · w-edge ◄─────► e-wan · e-srv ◄─────► s-edge
       access link (netem)                    CAKE (egress)
```

Default egress mode today:

- up: client → `c-cli` → `ns_wan` → `w-edge` → `e-wan` → `e-srv` (CAKE) →
  server;
- down: server → `e-srv` → `e-wan` (CAKE) → `w-edge` → `c-wan` (netem) →
  `c-cli`.

Ingress mode changes only the down shape point:

```
server ──► e-srv ──► e-wan ──► w-edge ──► c-wan (netem) ──► c-cli
                                                              │ ingress
                                                              ▼
                                                            ifb0 (CAKE ingress)
```

- `ifb0` lives in `ns_client`.
- The ingress qdisc and `mirred` filter live on `c-cli`.
- The download egress CAKE on `e-wan` is **absent**.
- The upload egress CAKE on `e-srv` remains; it is not on the download path.
- `CGO_SHAPE_MODE=ingress` makes `ProdDepsDualNS` use
  `TCShaper=NsRunner{ns_client}`, `ShaperIf=ifb0`, and poll `ifb0` for
  stats.
- The netem stays on `c-wan` for the down direction and on `w-edge` for the
  up direction, exactly as before.

The client namespace also hosts the probes. That is a bench shortcut: a real
CPE would forward to a LAN, while this bench terminates the download at the
same namespace. It is acceptable for comparing AQM behavior at the receive
side, and it must be stated in the thesis. It is not a claim that the bench
models a full CPE topology.

### 3.1 Fail-closed preflight

Before `applyPhysics` (the first netem/`tc` mutation of a cell), the campaign
runs `qdisc.CheckIngress`, which reads only:

1. `ip -o link show dev ifb0` — the device exists and its flags contain `UP`.
2. `tc qdisc show dev c-cli` — an `ingress` qdisc exists.
3. `tc filter show dev c-cli parent ffff:` — a `mirred` action targets
   `ifb0`.

Any failure aborts the cell with a named error and no qdisc mutation. The
preflight does not probe the CAKE rate; that is the campaign's job. It also
does not create the device; the bench owns it.

### 3.2 Bench commands

`kit/cgo-bench-dualns.sh up --ingress on` adds, after the usual namespace and
address setup:

```bash
ip netns exec ns_client ip link add ifb0 type ifb 2>/dev/null || true
ip netns exec ns_client ip link set ifb0 up
ip netns exec ns_client tc qdisc del dev c-cli ingress 2>/dev/null || true
ip netns exec ns_client tc qdisc add dev c-cli handle ffff: ingress
ip netns exec ns_client tc filter add dev c-cli parent ffff: protocol all \
  matchall action mirred egress redirect dev ifb0
ip netns exec ns_client tc qdisc replace dev ifb0 root cake \
  bandwidth "${RATE_MBIT}mbit" rtt "${RTT_MS}ms" ingress
```

and skips the `e-wan` download CAKE. `check` verifies the three plumbing
facts, requires CAKE on `ifb0`, and rejects CAKE on `e-wan`. `show` prints
`ifb0`, the `c-cli` ingress qdisc, and the filter. `down` deletes the
namespaces, which removes `ifb0`; no module unload is needed.

`check` and `show` must be told the mode too: pass `--ingress on` or export
`CGO_SHAPE_MODE=ingress`. `up --ingress on` does not persist a mode for later
invocations. The bench also defaults its mode from `CGO_SHAPE_MODE=ingress`
when `--ingress` is absent, so the `cgo run` preflight (which has no flag of
its own) checks the same topology as the campaign.

`kit/run-dualns.sh up --ingress on` passes the flag through to the bench for
`up` and `serve`. It does not set `CGO_SHAPE_MODE`; the campaign env remains
the operator's explicit choice.

## 4. Production remediation

### 4.1 Linux command set

`remediate.LinuxTCIngress(l, qdisc)` emits, in order:

1. delete the old ingress qdisc on the WAN interface (`|| true`);
2. delete the old `ifb0` root qdisc (`|| true`);
3. `modprobe ifb sch_ingress act_mirred cls_matchall 2>/dev/null || true`;
4. create `ifb0` if absent, then set it up;
5. add `handle ffff: ingress` on the WAN interface;
6. add `protocol all matchall action mirred egress redirect dev ifb0`;
7. attach the requested qdisc to `ifb0`.

CAKE line:

```
tc qdisc replace dev ifb0 root cake bandwidth <95%> rtt <rtt>ms \
  ingress dual-dsthost nat diffserv4 [overhead N]
```

- `ingress` is the CAKE ingress mode from tc-cake(8); it is not a generic
  qdisc option and must not be added to tbf/fq_codel.
- `dual-dsthost` is the documented flow mode for ingress-to-LAN fairness;
  `triple-isolate` remains the campaign default, so the production script is
  a prescription, not a replay of the measured cell.
- `ack-filter` is deliberately absent: the downlink data stream is not an
  ACK stream. The upload script keeps it.
- `nat` helps fairness when the router NATs; if it does not, it is a no-op.
- `diffserv4` gives the telemetry class its own tin, matching the upload
  script's production intent.

`fq_codel` and `pfifo_fast` use a tbf root on `ifb0` plus the same
ingress/redirect plumbing. No `ingress` keyword is emitted for them; it is
CAKE-specific. `pfifo_fast` remains a baseline, not a recommendation.

### 4.2 RouterOS script

`remediate.RouterOSIngress(l, qdisc)` requires `Link.RouterOSLanInterface`.
It emits an idempotent queue tree parented on that LAN interface:

```
/queue tree remove [find where comment="cgo-managed-ingress"]
/queue type remove [find where name~"^cgoingress-"]

/queue type add name=cgoingress-cake kind=cake \
    cake-bandwidth=<bits> cake-rtt=<rtt>ms \
    cake-flowmode=dual-dsthost cake-nat=yes cake-diffserv=diffserv4 \
    cake-wash=yes
/queue tree add name=cgoingress-lan-in parent=<lan> max-limit=<bits> \
    queue=cgoingress-cake comment="cgo-managed-ingress"
```

Why the LAN interface, not the WAN: RouterOS's queue tree is
one-directional; upload traffic reaches the public/WAN interface, download
traffic reaches the private/LAN interface. The official queue-tree docs say
so. There is no documented IFB or `global-in` download queue-tree substitute;
the script must not pretend there is.

Why `cgoingress-*`: the existing upload cleanup removes types matching
`^cgo-` and queues matching `comment="cgo-managed"`. `cgoingress-` does not
match `^cgo-`, so running the upload script cannot delete the download
objects. The ingress cleanup matches only `^cgoingress-` and its own comment.
A both-direction report can therefore be pasted one script at a time without
cross-deletion.

`fq_codel` maps to sfq with the same "not fq_codel" note as the upload
script; `pfifo_fast` maps to fifo.

### 4.3 Direction-aware report

`BuildReport` reads `res.Direction`:

| `res.Direction` | Up capacity | Down capacity | Emitted remediation |
|---|---|---|---|
| `""` / `"up"` | `res.ThroughputMbps` | — | `LinuxTC`, `RouterOS` (unchanged) |
| `"down"` | — | `res.ThroughputMbps` (headline is the down window) | `LinuxTCIngress`, `RouterOSIngress` |
| `"both"` | `res.ThroughputMbps` | `res.ThroughputDownMbps` | both, sized separately |

Rules:

- `Link.RTTms` is `res.RTTIdleP50` for both directions.
- If a `both` result has no down capacity, the report emits the up
  remediation and adds an `Unavailable{Metric:"remediation (download)"}`
  entry. It does not size a download from the upload number.
- Conversely, if a `both` result has no up capacity, it emits the down
  remediation and adds `Unavailable{Metric:"remediation (upload)"}`. It does
  not size an upload from the download number.
- If a down result has no capacity, the existing `remediation` unavailable
  entry is used.
- If `Link.Interface` is empty, Linux generation fails and no Linux command
  is emitted; the report does not invent an interface. RouterOS generation
  still depends on its own named interface, as today.
- Down-only does not print the upload section. `linux_tc` is an empty array
  (not `null`) for JSON consumers; `linux_tc_ingress` and
  `routeros_ingress` are additive and omitted when empty.

`Remediation` gains:

```go
LinuxTCIngress []string `json:"linux_tc_ingress,omitempty"`
RouterOSIngress string  `json:"routeros_ingress,omitempty"`
```

Markdown headings become direction-specific:

- `### Linux — upload (egress)` for `LinuxTC`;
- `### Linux — download (ingress IFB)` for `LinuxTCIngress`, with one
  sentence that the IFB shapes the download after the packet has crossed the
  link and `ack-filter` does not apply; when the qdisc is CAKE, state that it
  is in ingress mode;
- `### MikroTik RouterOS v7+ — upload (WAN)` for `RouterOS`;
- `### MikroTik RouterOS v7+ — download (LAN queue tree)` for
  `RouterOSIngress`, with one sentence that RouterOS has no IFB.

The root `## Remediation` header and `Recommended qdisc` line stay. The
qdisc reason is shared; for a down-only report it is replaced with a
download-specific sentence so the report does not justify the choice with
an upload-only `ack-filter`.

The `/api/remediate` endpoint returns the whole `Remediation` struct, so the
new fields are additive there. The audit-start body gains `routeros_lan`;
the CLI gains `--ros-lan`. The dashboard's `AuditReportCard` is untouched in
this slice; TypeScript ignores the new JSON fields. The Markdown report
already contains the ingress script for operators who download it.

## 5. Campaign ingress mode

`Deps` gains:

```go
// ShapeMode — "egress" (défaut) ou "ingress" (IFB sur l'ingress WAN).
ShapeMode string
// IngressPreflight — lecture seule de ifb0/ingress/mirred, AVANT toute
// mutation qdisc. nil en mode ingress ⇒ la cellule est refusée.
IngressPreflight func() error
```

`ProdDepsDualNS` adds the env wiring:

| Env | Default | Meaning |
|---|---|---|
| `CGO_SHAPE_MODE` | `egress` | `egress` or `ingress`; any other value is refused by `RunEvent`. |
| `CGO_CLIENT_NS` | `ns_client` | Namespace that owns `ifb0` in ingress mode. |
| `CGO_INGRESS_IF` | `c-cli` | WAN device whose ingress is redirected. |
| `CGO_INGRESS_DEV` | `ifb0` | IFB device that carries the shaper. |

In ingress mode:

- `TCShaper = qdisc.NsRunner{Ns: CGO_CLIENT_NS}`;
- `ShaperIf = CGO_INGRESS_DEV`;
- `IngressPreflight = qdisc.CheckIngress(NsCommand{client}, ingressIf,
  ingressDev)`;
- `StatsFn` polls `ifb0` in the client namespace;
- `TC` remains the netem runner in `ns_wan`; `CliIf`/`PhysicsIfaces` are
  unchanged.

`RunEvent` order:

1. `defaults` (sets `ShapeMode=egress` if empty);
2. validate `ChannelModel` (existing, pre-mutation);
3. validate `ShapeMode` and its constraints:
   - `ingress` requires `Bench=="dualns"`;
   - `ingress` requires `Direction=="down"`;
   - `ingress` requires a non-nil `TCShaper`, a non-empty `ShaperIf`, and
     a non-nil `IngressPreflight`;
   - any other mode string is refused;
4. run `IngressPreflight` (read-only);
5. `applyPhysics` (existing);
6. reset the shaper device root and select `d.TCShaper`/`d.ShaperIf`
   (existing, now `ifb0` in ingress mode);
7. apply:
   - ingress: `qdisc.ApplyIngressShaper(shaper, shaperIf, ev.Qdisc,
     prof.CapDown(), prof.DelayMs)`;
   - down egress: existing `ApplyShaper` on `e-wan`;
   - up egress: existing `ApplyShaper` on `e-srv`.

The reset/defer block remains: it deletes the root qdisc on `ifb0` before the
cell and again on exit. It does **not** delete the `c-cli` ingress qdisc or
the `mirred` filter; those are bench-owned and survive the campaign. The
next cell's `ApplyIngressShaper` replaces the `ifb0` root qdisc; the bench's
`check` after a campaign may report no CAKE on `ifb0` until the next `up`,
exactly as the egress bench already does for `e-wan`.

`ApplyIngressShaper` uses the same `model.Qdisc` switch as the egress
campaign:

- CAKE: `tc qdisc replace dev ifb0 root handle 1: cake bandwidth X rtt Y
  ingress` (no diffserv/ack-filter/nat);
- fq_codel: tbf root + fq_codel child;
- pfifo_fast: tbf root.

If the mode is `egress`, no ingress branch runs and the existing tc call
sequence is unchanged. Tests assert that.

## 6. Accounting and honesty

- **Drops at the IFB are host drops.** They are the AQM's response to a queue
  that formed after the packet crossed the emulated link. They are not drops
  at the remote sender and not proof of link-level loss.
- **CAKE `ingress` counts dropped bytes as transferred.** `tc -s` bytes and
  drops in ingress mode therefore do not mean the same thing as in egress
  mode. Any thesis table that compares them must carry this note.
- **RTT includes the netem link and the IFB queue.** The bench puts the
  netem upstream of `c-cli`; the IFB queue is downstream. The report must not
  subtract idle RTT and call the remainder "queue dwell" at the remote link.
- **RouterOS is not an IFB.** The LAN queue tree is an egress queue on the
  LAN interface. It shapes the same download direction, but at a different
  point. Do not present it as a byte-for-byte equivalent of the Linux IFB.
- **The bench is not a full CPE.** The LAN behind the client is not modeled.
  The result is a comparison of AQM behavior at the receive side, not a
  claim about a production CPE's forwarding path.
- **No live claim before Task 9.** The Windows tests prove the command
  strings, the report fields, and the fail-closed ordering. They do not prove
  that a kernel accepts the commands or that the IFB drops packets.

### 7.2 Linux 6.8 live acceptance (blocked)

On the stable bench:

1. `run-dualns.sh up --ingress on`; `cgo-bench-dualns.sh check --ingress on`
   passes.
2. `CGO_SHAPE_MODE=ingress cgo run --bench dualns --direction down
   --profiles P2 --qdiscs cake --cc bbr --reps 1 --flows 4` completes.
3. While the cell is in its charge window, a second shell samples
   `ip netns exec ns_client tc -s qdisc show dev ifb0`: it shows
   `cake … ingress` and non-zero drops/bytes. `tc filter show dev c-cli
   parent ffff:` shows the redirect. After the cell, the campaign's deferred
   cleanup removes the `ifb0` root qdisc, so a post-run sample showing
   `noqueue` is expected, not a failure.
4. `e-wan` has no CAKE; the download is not pre-shaped.
5. A down audit, run after `run-dualns.sh up --ingress on` restores the bench
   and from inside `ns_client` so it reaches the sink, produces
   `linux_tc_ingress` with the measured rate and a `routeros_ingress` script
   when `--ros-lan` is supplied.
6. A post-run `run-dualns.sh down` removes the namespaces; no `ifb0` leak.
7. Record the evidence in the plan and the roadmap. If any step fails, record
   the failure; do not mark the slice verified.

## 8. Risks and limits

| Risk | Mitigation |
|---|---|
| IFB copy/queue costs CPU | This is a single-flow bench at ≤20 Mbit/s; the cost is acceptable and documented. Do not extrapolate to 1 Gbit/s. |
| `ingress` accounting differs from egress | State it in every drop/byte comparison; use the same CAKE parameters in cells. |
| Bench `e-wan` left with CAKE | Bench `check` refuses it in ingress mode; the campaign preflight is separate but cannot see `e-wan`. Restart the bench without `--ingress on` before an egress down campaign. |
| RouterOS attach point differs | Label the script as a LAN egress queue tree; do not call it IFB. |
| VM/host instability | Task 9 stays blocked until the Linux 6.8 bench is stable; Windows gates do not depend on it. |
| Global env leaks into an up campaign | `RunEvent` refuses ingress with `up`/`both`; the error is explicit. Run ingress campaigns with `--direction down`. |
| `cgoingress-*` name collision | The prefix is disjoint from `^cgo-`; a test asserts both scripts' cleanup markers. |
